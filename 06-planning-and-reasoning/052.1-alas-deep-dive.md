# ALAS 事务性规划深度解析

> 本文是 [052-plan-and-solve-replanning.md](./052-plan-and-solve-replanning.md) 第九节策略 3 的补充阅读。

---

## 核心思想

借鉴数据库事务（ACID）模式，把每个规划步骤当作一个**原子、可撤销的操作**，给 Agent 装上一个"撤销按钮"。

---

## 数据库类比

| 数据库事务 | ALAS Agent 步骤 |
|---|---|
| `BEGIN` — 快照当前数据 | `checkpoint = save_state()` — 快照 Agent 状态（上下文、工具输出、记忆） |
| 执行 SQL | 执行规划步骤 |
| `COMMIT` — 保留变更 | `commit(result)` — 保留步骤结果，继续前进 |
| `ROLLBACK` — 撤销变更 | `rollback(checkpoint)` — 恢复到步骤执行前，就像这步从未发生 |

---

## 每个步骤的三种结局

```
执行步骤
    │
    ├── 成功 + 验证通过 ──► commit(result)          ✅ 继续下一步
    │
    ├── 成功但验证不通过 ──► rollback + 换方式重试    🔄
    │
    └── 抛异常 / 出错 ──► rollback                   ❌
              │
              ├── 还有重试次数 ──► retry(step)        🔄 再来一次
              └── 没有重试机会 ──► replan()           🗺️ 从这里重新规划
```

---

## 为什么重要？

没有事务性规划时，Agent 走错一步，错误结果已经**污染了上下文**（LLM 记忆、工具状态），会影响后续所有决策。

有了事务性规划，每步执行前先拍快照，失败了就回滚到干净状态，再换策略重试或重新规划。

---

## 具体例子

任务："找到 X 公司 CEO 并发邮件"

```
步骤1：搜索 CEO 姓名 → "John Smith"        ✅ commit
步骤2：查找邮箱      → "john@companyx.com"  ✅ commit
步骤3：发送邮件      → ❌ 失败（邮箱地址无效）
        → rollback 到步骤3之前的状态（无效邮箱被撤销）
        → retry：尝试 "john.smith@companyx.com"
        → 还是失败 → replan：换思路，通过 LinkedIn 找 CEO
```

---

## 适用场景

长链路、多步骤任务，某一步失败**不应毁掉前面所有的进展**，需要局部回滚 + 局部重试的能力。

---

## 与 DuSAR 的对比

| 维度 | ALAS | DuSAR |
|---|---|---|
| **核心关注** | 怎么保证每步不出错 | 怎么规划 + 怎么越做越好 |
| **解决的问题** | 单步失败的状态污染 | 长时域任务的规划适应性 |
| **关键机制** | 快照 + 回滚 + 重试 | 经验库 + 动态重新拆解 |
| **类比** | 一个有撤销键的编辑器 | 一个有经验的项目经理 |
| **互补关系** | 管"执行层面"，可结合 DuSAR 使用 | 管"规划层面"，可结合 ALAS 使用 |

---

## 一句话总结

ALAS 把每个规划步骤当作一个**原子、可撤销的操作**，给 Agent 装了一个"撤销按钮"——成功提交，失败回滚重试，特别适合状态敏感、单步失败代价高的长链路任务。
